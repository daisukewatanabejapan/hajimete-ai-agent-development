# AIエージェント開発の設計パターン集

設計パターンは「よくある問題への、再利用しやすい解き方」です。最初から全部を使わず、必要なものだけを組み合わせます。

## 1. Draft → Human Review

AIは案を作り、最終決定は人が行います。

```text
入力 → AIが下書き → 機械的な検証 → 人が承認 → 実行
```

メール、公開文章、コード変更など、間違いの影響が大きい処理の出発点に向いています。

## 2. Read Before Write

最初に読み取り専用の道具で状況を確認し、更新は別の道具と承認に分けます。

```text
検索・参照 → 変更案 → 承認 → 更新
```

データベース、Issue、クラウド設定を扱う場合に有効です。

## 3. Router

入力を分類し、専門処理へ振り分けます。

```text
問い合わせ → 分類 → 質問 / 不具合 / その他
```

分類先を少なく保ち、判断できない場合の行き先を必ず用意します。

## 4. Plan → Execute → Verify

複雑な作業では、計画、実行、検証を分けます。

```text
目的 → 計画 → 小さな実行 → テスト → 次の実行
```

コード移行や複数ファイルの変更に向きます。計画は固定せず、発見に応じて更新します。

## 5. Bounded Retry

失敗時の再試行回数と終了条件を決めます。

```text
実行 → 失敗 → 原因を確認 → 最大2回だけ再試行 → 人へ渡す
```

無限ループ、API費用の増大、同じ更新の重複を防ぎます。書き込み処理の再試行では、二重実行を防ぐ仕組みも必要です。

## 6. Evidence First

回答や判断と一緒に、根拠を返します。

```text
検索 → 根拠を選ぶ → 回答案 + 参照元 → 人が確認
```

社内FAQ、規約、技術調査に向きます。根拠が見つからない場合は推測させません。

## 選び方

| 状況 | 最初に使うパターン |
| --- | --- |
| 外部へ送信・公開する | Draft → Human Review |
| データを更新する | Read Before Write |
| 種類の違う依頼が届く | Router |
| 作業が複雑 | Plan → Execute → Verify |
| 外部サービスが不安定 | Bounded Retry |
| 正確さと説明責任が重要 | Evidence First |

最初のおすすめは、`Draft → Human Review` と `Plan → Execute → Verify` の組み合わせです。
