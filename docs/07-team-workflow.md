# チーム開発での運用例

AIを「新しいチームメンバー」ではなく、指示と確認が必要な開発ツールとして運用します。

## 基本フロー

```text
Issueを書く → AIが計画を提案 → 人が確認 → AIが実装
→ CI → AIが自己レビュー → 人がレビュー → マージ
```

## 1. Issue

Issueには目的、変更範囲、完了条件、対象外を書く担当者は人です。曖昧な要件をAIだけに決めさせません。

## 2. 計画

複数ファイルや設計変更を含む場合は、AIに短い計画を作らせます。チームはAPI変更、データ移行、権限、ロールバックを確認します。

## 3. 実装

- 1つのPRに1つの目的
- 関係のないリファクタリングを混ぜない
- 小さなコミットまたはレビューしやすい差分
- 秘密情報をプロンプトへ渡さない

## 4. 自己レビュー

AIに差分を読ませ、次を確認させます。

```text
この差分をレビューしてください。
不具合、セキュリティ、互換性、テスト不足を優先し、
問題があるファイルと理由を示してください。
```

AIの自己レビューは人のレビューの代わりではありません。

## 5. 人のレビュー

人は特に、要件の正しさ、設計判断、権限、個人情報、運用への影響を確認します。

## 6. 振り返り

繰り返し起きる指摘は、次の場所へ戻します。

- リポジトリ全体の決まり → `AGENTS.md`
- 一度だけの条件 → Issueまたは依頼文
- 機械的に判定できるもの → lint、テスト、CI
- 複雑な定型作業 → 再利用可能なワークフロー

## 導入の目安

最初の2週間は、AIが作ったすべての差分を人が確認します。レビュー指摘、手戻り、テスト失敗を記録し、安全な作業から対象を広げます。
