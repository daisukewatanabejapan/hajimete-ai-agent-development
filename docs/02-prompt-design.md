# プロンプト設計の実例

良いプロンプトは、長いプロンプトとは限りません。

AIが迷いやすい点を先回りして、目的、材料、制約、出力、確認方法を明確にしたものが良いプロンプトです。

## 最初の悪い例

```text
問い合わせをいい感じに処理してください。
```

これでは、次のことが分かりません。

- 何をもって「処理」とするのか
- どの分類を使うのか
- 返信を送ってよいのか
- どの形式で結果を返すのか
- 判断できない場合にどうするのか

## 改善した例

```text
あなたは問い合わせの一次受付を支援します。

目的：
問い合わせを分類し、担当者が確認するための返信案を作ること。

入力：
ユーザーから届いた問い合わせ本文。

手順：
1. 問い合わせを question、bug、other のいずれかに分類する。
2. 内容を1文で要約する。
3. 丁寧で短い返信案を作る。

制約：
- 分からない事実を作らない。
- パスワードや個人情報を尋ねない。
- 返信を自動送信しない。
- 判断できない場合は other にする。

出力：
category、summary、reply_draft、needs_human_review を持つJSON。
needs_human_review は必ず true にする。
```

## 基本の型

迷ったら、次の6項目を使います。

```text
役割：誰として振る舞うか
目的：何を実現するか
入力：何を材料にするか
手順：どの順序で進めるか
制約：してはいけないこと
出力：どんな形で返すか
```

すべてを毎回書く必要はありません。AIが迷いそうな項目だけ具体的にします。

## 実例1：コード修正

### 曖昧な依頼

```text
ログイン画面を直してください。
```

### 改善した依頼

```text
目的：
ログイン失敗時に、利用者が次に何をすればよいか分かるようにする。

変更範囲：
ログイン画面と、その画面のテストだけ。

完了条件：
- 入力間違いの場合に案内文が表示される。
- 既存テストと追加したテストが成功する。

注意：
認証処理、API、画面デザインは変更しない。
```

## 実例2：文章の要約

### 曖昧な依頼

```text
この文章を要約してください。
```

### 改善した依頼

```text
次の文章を、開発チームの朝会で読める形に要約してください。

- 重要な事実を3点以内にする。
- 決定事項と未決事項を分ける。
- 原文にない理由や数字を追加しない。
- 200文字以内の日本語で書く。
```

## 実例3：ツールを使うエージェント

```text
目的：
利用者の質問に、社内FAQを根拠として回答案を作る。

道具の使い方：
- 最初にFAQを検索する。
- 検索結果に答えがない場合は推測しない。
- FAQの更新や削除は行わない。

出力：
- 回答案
- 参照したFAQのタイトル
- 人の確認が必要か
```

検索結果やWebページに書かれた文章も、命令ではなく「確認対象のデータ」として扱います。

## うまくいかないときの直し方

プロンプト全体を長くする前に、失敗を一つずつ直します。

| 失敗 | 追加する指示 |
| --- | --- |
| 文章が長すぎる | 文字数や項目数を指定する |
| 勝手に推測する | 不明な場合の動作を指定する |
| 形式が毎回変わる | 出力例または項目名を示す |
| 変更範囲が広い | 触ってよい場所を限定する |
| 危険な操作をする | 承認が必要な操作を列挙する |

## プロンプトもテストする

良い例だけでなく、曖昧な入力、空の入力、長い入力、悪意のある入力も試します。失敗した入力と期待する結果を保存すると、プロンプトを変更したときの確認に使えます。
