# 実際の失敗例と改善例（Before / After）

ここでの例は、AIエージェント開発で起こりやすい失敗を単純化したものです。

## 1. 変更範囲が広がった

### Before

```text
ログイン周りをきれいにしてください。
```

画面修正のつもりが、認証処理や依存関係まで変更されました。

### After

```text
ログイン失敗時の案内文を改善してください。
変更対象は LoginForm とそのテストだけです。
認証API、依存関係、デザインは変更しないでください。
```

## 2. 存在しない事実を回答した

### Before

```text
FAQを参考に回答してください。
```

FAQに情報がないとき、AIがもっともらしい回答を作りました。

### After

```text
FAQに明記された内容だけを使ってください。
答えが見つからない場合は「確認が必要」と返し、推測しないでください。
参照したFAQのタイトルも返してください。
```

## 3. テストを実行したと思い込んだ

### Before

```text
最後にテストしてください。
```

どのコマンドか不明で、実行されないまま完了扱いになりました。

### After

```text
npm test と npm run lint を実行してください。
実行できない場合は、成功とは書かず、コマンドと理由を報告してください。
```

## 4. 自動送信してしまった

### Before

エージェントにメール作成と送信の両方の権限を与えました。

### After

下書き作成と送信を別の操作にし、送信前に人の承認を必須にします。

## 5. 同じ処理を何度も実行した

### Before

失敗したら成功するまで再試行する設計でした。

### After

最大再試行回数、待ち時間、人へ引き継ぐ条件を決めます。書き込みには重複防止用のIDを使います。

## 6. `AGENTS.md` が抽象的だった

### Before

```markdown
- 高品質なコードを書いてください。
- ベストプラクティスに従ってください。
```

### After

```markdown
- 変更後に `go test ./...` を実行してください。
- 公開APIを変える場合は先に影響を説明してください。
- 不具合修正では再発防止テストを追加してください。
```

抽象的な理想より、実行できるコマンドと判断基準を書きます。

## 振り返りの型

```text
期待したこと：
実際に起きたこと：
原因：
次回追加する制約またはテスト：
```

失敗した入力を消さず、テストケースへ変えることが改善の近道です。
